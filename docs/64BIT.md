# Pointers and the 64-bit engine

The game code is decompiled from the PS1, where a pointer is 4 bytes, and it reads the disc's level, model and nav files in place. The rules below keep that working whatever the host's pointer size, so the same code builds as 32-bit x86 and as 64-bit x86_64 or arm64 (`-DCTR_64BIT=ON`, the default on a 64-bit compiler outside Windows).

## Releases
- **Linux** ships the 64-bit engine for x86_64 and arm64 (`build.yml`), so players need no 32-bit libraries and ARM computers run it natively. The 32-bit Linux build (`-DCTR_64BIT=OFF`) is not released; it stays the reference for the bit-exact comparisons below.
- **Windows** ships the 32-bit build: it runs on every Windows PC, ARM ones included through their x86 emulation, and a 64-bit build would gain players nothing. CI keeps the 64-bit Windows build compiling (`windows-64bit` in `build.yml`).
- **macOS** ships the 64-bit build for Apple Silicon as an app bundle ([MACOS.md](MACOS.md)).
- Each client archive is a target of the in-game updater (`Target` in `ap/ap_update_core.h`; `TARGETS` in `tools/release/release_policy.py`), so adding one changes the signed manifest every client reads ([RELEASING.md](../RELEASING.md#signed-client-manifest)).

## Two kinds of struct
- **Disc-format.** Its bytes come from a file: the LEV (`struct Level` and everything it reaches: `mesh_info`, `QuadBlock`, `BSP`, `PVS`, `VisMem` and its lists, `InstDef`, `AnimTex`, spawn tables, `Skybox`, icon packs), models (`Model`, `ModelHeader`, `ModelAnim`), MPK packs (`struct ModelPack`), nav paths (`NavHeader`). It keeps retail's byte layout on every build, and a pointer field in it is a `PSX_PTR(T)`.
- **Runtime.** Everything the game allocates and fills itself (`Instance`, `Driver`, `Thread`, `GameTracker`, `CameraDC`...). Plain C with native pointers. Its retail offsets and sizes are asserted with `CTR_RETAIL_LAYOUT_ASSERT`, which checks them where pointers are 4 bytes; a disc-format struct's use `CTR_STATIC_ASSERT` and hold on every build.

`Instance` is the one runtime struct a disc slot points at (`InstDef.ptrInstance`, the PVS instance lists); instances come from a pool inside PSX space.

## PSX space and PSX addresses
`include/ctr_psx_ptr.h`, `platform/native_psx_space.c`.
- PSX space (`gPsxSpace`) is one static host block: the mempack backing first (`platform/native_memory.c`), then a heap (`PsxSpace_Alloc`, `PsxSpace_Free`).
- A `PSX_PTR` holds a PSX address: `0x80000000` plus the target's offset in PSX space, or 0 for NULL. Under retail memory pressure the mempack backing is the 2 MiB PS1 RAM image, so stored values are the addresses retail keeps in RAM: compare level data with PCSX-Redux directly, and retail's sign tests on pointer words work unchanged.
- `PSX_GET(p)` gives the typed host pointer, `PSX_SET(p, v)` stores one (type-checked), `PSX_ADDR(p)` is the raw word. `PSX_PTR` is a union, so using a field without them does not compile: the compiler lists every site. The union is pinned to 4-byte alignment; its type-carrying member would otherwise give it a host pointer's 8 and pad every disc struct.
- `LOAD_RunPtrMap` adds the file's PSX address to each slot its pointer map names.
- A pointer to an array of PSX pointers is `Psx<Type>Ptr *` (`PsxModelPtr`, `PsxIconPtr`...): each element needs its own `PSX_GET`. Accessors for the arrays that follow a header: `ST1_GETPOINTER`, `ANIMTEX_GETFRAME`, `ICONGROUP_GETICON`.

## Rules
- **Disc-format data lives in PSX space.** A file read by the host and relocated (racer and bot models, Archipelago harvests, the Oxide menu model, the Archipelago title Roo), or disc-format data the host builds (Archipelago box, marker and beam models, recorded nav lanes, the blank nav template, missing VisMem lists), is allocated with `PsxSpace_Alloc`, never `malloc` or a static array. Storing a pointer outside PSX space is a fatal error that names it.
- **No raw reads of pointer slots.** `*(struct X **)p`, `(struct X *)*(u32 *)p` or a `memcpy` between a disc struct and a runtime struct read a PSX address as a host pointer. Go through the typed field or the accessors above. A copy between the two kinds is field by field (`INSTANCE.c`, level instance birth).
- **Records told apart by where they live.** The InstDef/Instance lists swap in place (`LevInstDef.c`); retail finds the peer at offset 0x2c of either, native knows an Instance by its pool.
- **Pools hold the 64-bit size.** A runtime struct is at most twice its retail size on a 64-bit host: every field at most doubles, and so does every offset. Thread object pools (`THREAD_*_STACK_SIZE`) hold twice retail's object there, and the retail-pressure mempack arena is twice as long from retail's start (so level data keeps retail's addresses); both are retail's on 32-bit, so memory pressure and the bit-exact runs do not change. Pools take their item sizes from `sizeof` (`NativeSpawnPools_Plan` gets them from its caller).
- **No pointers in 32-bit integers.** The 64-bit build makes casts between pointers and narrower integers errors (`-Werror=pointer-to-int-cast`, `-Werror=int-to-pointer-cast`). Address arithmetic goes through `u8 *`; an address kept as a number is a `uintptr_t`, never a `long` (32 bits on 64-bit Windows); a field or variable that holds a pointer has a pointer type. A cast through `size_t` first (`(s32)(size_t)p`) hides the truncation from the compiler, so it is never written. In a register-matched function a register variable that carries pointers as well as numbers is a `CtrPsxReg` (`CtrPsxSReg` when the function also compares it as signed): `u32`/`s32` on the PS1, so the matched code does not change, and pointer-wide natively.
- **Formats match their arguments.** A pointer difference or `size_t` passed to `%d` shifts every later argument on a 64-bit host (a `%s` after it reads a wrong pointer); the 64-bit build makes format mismatches errors (`-Werror=format`). Cast a small difference to `int`, or print a `uintptr_t` with a matching format.
- **Plain `char` is signed** on every build (`-fsigned-char`), as on the PS1 and x86; arm64 Linux would make it unsigned. `long` is 64 bits on Linux and 32 on Windows, so game data never uses it.
- **Every library that includes engine headers defines `CTR_NATIVE`** (the engine, the custom package library, the Archipelago network library). Without it the headers take the PS1 branch and declare their own `size_t` and `uintptr_t`, four bytes wide.
- **A fixed-layout record that points into PSX space keeps a PSX address.** Where retail's layout of a runtime record or scratchpad word matters (its size sets how many fit, or numbered offsets reach past it) and what it points at lives in PSX space, the word is a `PSX_PTR` or a PSX address and keeps retail's four bytes: the level renderer's clip records (`otEntry`), the torch scratch, the ground shadow's driver records and OT word, and the instance OT ranges (`InstDrawPerPlayer.otRangeNormal`, which retail does 32-bit arithmetic on). For that, the memory they point at is in PSX space too: the mempack, its pools, and the instance ordering tables (`Platform_GetOTArena`).
- **Read runtime structs by field, size them by `sizeof`.** Code that reads a runtime struct at a retail byte offset (`*(u32 *)((u8 *)inst + 0xb8)`), copies one as a count of 32-bit words, clears one with a retail byte count, or writes a pointer through an `int *` reads and writes the wrong bytes once pointers widen. It names the field (`INST_GETIDPP(inst)->instFlags`), copies the struct, and takes `sizeof` or `offsetof` (`DRIVER_NTSC_RETAIL_SIZE` is `offsetof(struct Driver, ghostTape)`). Where a data table or matched code keeps retail offsets into a pointer-free block, one accessor rebases them (`DRIVER_META_PHYS_FIELD`, `VEH_EMITTER_SKID_BASE`). A loop that steps through a runtime struct one 4-byte word at a time to index a table counts the table instead (the level renderer's bucket dispatch counts bucket roles; `DRAW_LEVEL_OVR1P_BUCKET_RETAIL_OFFSET` gives retail's offset where a scratch word keeps it). Where retail's offset lands on a different field than it meant, the port names the field it actually reads (`RedBeaker_CloudDepthBias`) and asserts the retail offset. The compiler does not find these; a 64-bit run against the 32-bit captures does.
- **Scratchpad layouts follow their structs.** The native scratchpad is twice the PS1's 1 KiB on a 64-bit host (`CTR_SCRATCHPAD_SIZE`). Offsets numbered past a scratch struct that holds pointers are derived from it (`DRAW_LEVEL_OVR1P_*_OFFSET`, `RENDER_BUCKET_PAYLOAD_SCRATCH_OFFSET`, the skid renderer's `origin`) and assert retail's number with `CTR_RETAIL_LAYOUT_ASSERT`; code passes those names, never a literal offset. Where pointers and numbered words share scratch space (the level renderer's clip cursors in front of its depth thresholds, `MainRenderLevelGeometryScratch.reserved0`), the space is sized for host pointers.
- **Nothing drawn depends on where memory lies.** A table indexed by a hash of a host address evicts on collisions, and those differ between builds, so a lookup that can fail must fail the same way on every build: the precise renderer's address tables never evict during a frame ([PGXP.md](PGXP.md)).
- **Files keep their offsets.** A file whose 32-bit offsets retail turns into pointers in place keeps them natively. The language strings (`LOAD_LangFile_IndexStrings`) point a host array at the file's strings; the credits copy is read through `CS_CREDITS_STRING`, its base plus the offset, so a savestate moves only its table pointer.

## Floats
Every build rounds float math the same way, so the precise renderer ([PGXP](PGXP.md)) draws the same pixels on 32-bit x86, x86_64 and arm64: 32-bit x86 computes in SSE registers (`-msse2 -mfpmath=sse`) instead of the x87 FPU, whose wider intermediates round differently, and no build fuses a multiply and an add (`-ffp-contract=off`, which arm64 compilers would otherwise do). The game logic itself is integer-only.

## Checking
- The 32-bit build must stay bit-exact through any change here: capture frames, `CTR_DEV_TRACE` and `CTR_DEV_RESULTS` with `tools/decrypted/devrun.ps1` (title menu, attract demos, autopilot races, the N. Sanity Beach hub, a Gem Cup) before and after, and compare the files byte for byte.
- The PS1 byte-matching results must not change: run `tools/matching/match.py check --reference-root <dir>` before and after and compare the per-target lines. Its compiler is GCC 2.8.1 for Linux: from Windows run it in WSL on a copy of the tree in the Linux file system with LF endings (that `cpp` cannot `stat` files on `/mnt/c`, and it reads a backslash before `\r` as a stray character). The reference directory holds `SCUS_944.26` and the BIGFILE entries 221-233 as `bigfile/overlays/<name>.bin` (`tools/racers/ctrdisc.py` reads both; `metadata/retail/ntsc-u-926/matching.json` names them and their hashes).
- A 64-bit build is checked the same way: its captures, traces and results against the 32-bit build's. A polygon dump of the first differing frame from each (`CTR_DEV_DUMP_FRAME`, `CTR_DEV_VRAM_DUMP`) names the draw stage that differs; when the dumps match and the image does not, the difference is in what the dump does not list (lines, VRAM uploads).
- Linux and arm64 runs use `tools/decrypted/devrun.sh`. Traces, results, podiums and polygon dumps must match the Windows 32-bit build's: they do not depend on the OS or the GPU (compare text ignoring line endings). Frames match between builds that share a rasterizer: a 32-bit (`-m32 -msse`) and a 64-bit Linux build on the same machine both run Mesa's llvmpipe under Xvfb. arm64 on an x86_64 machine: cross-compile with `aarch64-linux-gnu-gcc` against `:arm64` multiarch libraries, then run with `-w qemu-aarch64`.
- A pointer squeezed into 32 bits only crashes when its target lies above 4 GB, which depends on where the host places memory: run a 64-bit scenario several times in parallel before calling it clean. A fixed-base Linux build keeps its statics (PSX space included) below 4 GB; build one with `-DCTR_FIXED_BASE=OFF` too, which is position-independent and loads them above 4 GB at a new address every launch, as macOS always does, and compare its runs with the fixed-base build's.
- A battle arena exercises the blank nav template; a converted custom track exercises the host VisMem lists and mover patterns. The Archipelago build's title screen exercises its relocated Roo model.
- Host harnesses link the real PSX space. One that includes engine code includes `platform/native_psx_space.c`; one whose fixture declares its own copies of disc-format structs includes `tools/harness-psx-space.h` (built with `-DCTR_NATIVE -I include`), declares their pointer fields with `PSX_PTR`, and allocates what they point at with `PsxSpace_Alloc`, so the production code under test runs on the same pointers as in the game.
